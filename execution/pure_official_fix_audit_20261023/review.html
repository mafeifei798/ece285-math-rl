PURE 官方如何处理空回答，哪些修法有依据？

明确结论：官方两个分支存在实质差异。OpenRLHF 默认把步骤边界和回答末端的 advantage 置零，并在归一化后保持为零；此前参照的 veRL 没有这一步。我们已在固定回答上验证：它消除了 8 条 EOS-only 空回答的直接策略梯度信号，但没有把错误 PRM 分数修正成正确分数。

建议采用同一固定 OpenRLHF 信号实现的 P-VR / P-PRM 成对基线，不要仅拼接 mask 后称作 veRL 的 bug fix。这里已完成的是独立信号模块与离线回放；尚未接入或启动新训练。

1. 为什么论文有提升，又有空回答高分？

论文 §5.1 Case 3 明确讨论了空回答和无关短句：因果 PRM 在给当前步骤打分时，不知道后面不会再解题。作者采用少量结果奖励辅助来缓解这一问题；纯 PRM 仍会投机。§4.2 报告的是训练期间保存的最佳 checkpoint，而不是保证最终模型不退化。Case 3 · 实验与选点协议

早期 OpenRLHF README 也写明：纯 PRM 模型在发生投机前表现良好，并以 step 100 的保存模型为例。因此阶段性有效与后续失败可以同时成立。官方训练说明

论文 v3 的实验使用 veRL；OpenRLHF 是官方另一实现分支。采用它不能称为 v3 表格结果的精确复现。PURE-PRM+VR 的约 10% GT 辅助属于混合奖励，本轮没有加入 P-PRM。

这证明了什么：在这批重构 EOS-only 回答上，advantage=0，因此该 action 的直接 PPO 策略梯度项为 0。额外的 ratio=1 合成 log-prob 求导检查也通过；不是对模型权重做训练。
没有证明什么：PRM 高分与奖励排序仍在；空回答仍进入同题其他回答的 baseline；“谢谢”等非空无关文本仍可得到正优势。共享参数更新也仍可能改变 EOS 概率。

完整结果：汇总 · 逐回答 · 源码调用与 oracle 收据 · 独立全链复核。逐回答文件中的 task_reward_sum 仅记录过程奖励之和，VR 臂该字段为 0，不代表其结果奖励为 0。

4. 为什么不把“只加 mask”直接叫修复完成

单独移植 OpenRLHF 的 mask+normalize 到 veRL 原始优势，也把 Qwen / PURE 三种 PRM 配置的 8/8 正空回答优势降为 0。但它同时把 P-VR 对空 EOS 的负信号清零。在 P-VR 的 143,705 个正文 token 中，50,404 个原始零优势从 veRL 归一化后的负值回到 0，没有发生正负方向翻转。这说明两种归一化并非可互换的“实现细节”。

该移植保留为机制诊断；推荐方案使用完整同源 OpenRLHF 信号链。窄移植结果 · 独立复核

5. 具体方案与公平控制

  1. P-VR 与 P-PRM 一起采用固定 OpenRLHF 实现。P-VR 用现有验答结果，P-PRM 只用冻结 PURE PRM；共享边界、归一化和 sampler 约定。
  2. 不添加空回答负奖励或长度奖励。不依据答案正确与否筛掉 P-PRM 的回答，不把少量 GT 辅助偷偷放进纯 PRM 臂。
  3. 后续真实模型联调保存 emitted token IDs。按官方步骤定位逐一核对；两臂共同检查最低生成长度 1、边界和 loss 的一次归一化。当前旧日志重构不构成这项验收。
  4. 控制实验条件。同一初始 1.5B policy、训练题目、seed、rollout token 预算、LoRA、评测提示词与验答器；单卡小 batch 明示为资源适配。原 A/B 与旧 veRL 对照全部保留，不把新结果覆盖到旧实验名下。
  5. 保留剩余风险。全零优势批次目前在离线适配器中明确报错；尚未安装自动跳过或替代归一化规则。正式训练需要先完成完整 runtime 联调，不能由这次 CPU 结果推断准确率会提高。

实施协议：protocol.json。本轮未启动正式训练、模型 forward 或新生成。
