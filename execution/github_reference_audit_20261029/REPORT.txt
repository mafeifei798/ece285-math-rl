GitHub 参考项目审查（2026-10-29）
共11个项目、12个固定分支/标签快照；9个项目核对了相关代码路径，PROF和DAPO限于文档/文件树及可访问性核查。未运行第三方训练，也未改动当前三组训练、奖励、loss、提示词或验答。

核心判断：保持当前 A / C-mix / C-bounded 三组小试，补清已有工作和贡献边界。PAPO是最接近的算法对照；PURE是信用分配和步骤/EOS接线参考；EasyR1适合参考资源受限工程组织；LCA对应已经进行的PRM适配来源。

与PAPO的实质关系：
1. 答对子集门控、结果与过程优势分开，已经是PAPO的明确设计，不能作为我们的原创。
2. PAPO默认过程项会除以正确子集std；我们的过程项是0.2*y*(m-mean_correct)，不再除std，且结果项继续使用原GRPO标准化。
3. 官方代码还有norm_adv_by_std_in_grpo=False分支，但该开关同时让结果项和过程项都只减均值。因此该分支与我们的混合缩放不同，但也说明“不除std”本身不是未被考虑的新想法。
4. 官方核心函数实际使用固定lambda；启动脚本头部仍有adaptive clipping字样。应以执行函数和所选commit为准，不能只抄注释。
5. PAPO公开配方使用生成式rubric评分、额外grader和多卡；我们的C是冻结判别式7B PRM。若后续加入同C评分器的PAPO式优势，只能称受控机制对照，不是完整PAPO论文复现。
6. 现有三组能回答有界方案是否优于纯结果奖励/简单混合，不能单独证明优于PAPO，也不能证明C适配优于原始未适配PRM。

证据与假设：
已核实：我们固定的TRL 0.23.1底层trainer与GitHub v0.23.1逐字节相同。reward加权后由trainer构造优势；loss读取inputs['advantages']，奖励回调返回的数不是梯度。
已核实：PAPO、PRIME、PURE具有不同的baseline、归一化和token/step处理路径；把min过程分加进GRPO不能称完整PURE。
待验证：保留判别式PRM原分差并限制幅度，是否比正确子集std缩放更适合小模型、有限预算的正常数学CoT。缩小幅度也可能削弱有用信号，不能预设更优。
待验证：正确答案内部的PRM排序是否可靠。最终答案正确不等于步骤正确；最终答案错误也不自动意味着每一步都错。

只做离线公式比较：
在已冻结C分数的67组/536条历史回答上，用标准库按核实公式重写PAPO过程项与当前方案比较，未调用模型或官方训练脚本。lambda统一为0.2并额外列PAPO默认1.0。所有正确子集门控版本错答正优势都为0，这不是本方法独有的成果。数值大小与答对样本优势符号的差异不代表数学能力优劣，详见offline_formula_check.json。不要把这张表当作PAPO论文复现或新模型评测。

建议落实顺序：
A. 当前训练设置冻结，按已经授权的1M三组小试完成；本轮不新增训练臂、模型或seed。
B. 论文/报告把PAPO列为最接近方法，给出公式和源码位置；把贡献限定为所研究设置下的信号保幅与受控实证，暂不称新算法。
C. 如果后续结果值得扩大，最有解释力的新增对照是同一C评分器、同样lambda、只把正确子集过程项改为PAPO式标准化；是否加入训练需另行决定，当前未排队。
D. 借鉴PURE的监控指标、SimpleRL的解答对比、EasyR1的环境锁定和恢复组织；这些属于可复现工程，不混进当前奖励/loss。

1. PAPO
https://github.com/tanzelin430/PAPO/blob/7d260f0a7a6e23d289e32bbc96f80408dddfa1d5/verl/verl/trainer/ppo/core_algos.py#L333
核查范围：核心优势函数、启动脚本及评分器代码已读
用途：最接近的方法对照
已核实：结果优势按整组归一化；过程优势仅在正确子集中计算并另行标准化。代码还允许两项一起不除标准差。
可借鉴：精确对照正确子集门控、过程项缩放、活跃组比例；当前三臂不会改动。
限制：默认配方需多GPU及额外生成式grader；不能直接照搬到单A100，也不能把我们的门控说成原创。

2. PURE
https://github.com/CJReinforce/PURE/blob/41f9363b8cc4af044b7fc5f7f9bbbf62139e9553/openrlhf/trainer/ppo_utils/experience_maker.py#L664
核查范围：OpenRLHF与verl两分支的信用分配及baseline代码已读
用途：过程奖励机制和诊断参考
已核实：官方OpenRLHF分支使用RLOO、步骤/原token/EOS与分步baseline；不是把整条回答的min分混进GRPO就等于PURE。
可借鉴：保留step/token baseline、EOS、重复/截断等诊断；分支和提交号必须固定。
限制：verl的compute_return(min)仍有作者TODO注释；仅凭注释不能断言整条路径有bug，使用前要逐例回放验证。

3. PRIME
https://github.com/PRIME-RL/PRIME/blob/18ad596f08d487bb546d80d738d99ec697bd2e75/training/README.md#L88
核查范围：训练文档与RLOO奖励合成源码已读
用途：隐式PRM相关工作
已核实：隐式过程奖励通过结果监督更新，与结果奖励分别做leave-one-out后合成，包含在线PRM更新及prompt过滤。
可借鉴：借鉴多奖励源分开记录和成本核算；引用时区分隐式PRM与显式判别式PRM。
限制：引入完整在线PRM更新会改变当前固定C实验，不作为本轮迁移目标。

4. PRPO
https://github.com/SchumiDing/srpocode/blob/662bbc6c2815900ca96e39106f31e8988f2d961a/verl2/verl/trainer/ppo/ray_trainer.py#L1145
核查范围：熵分段、多个reward manager、actor优势赋值路径已读；论文配置映射未完全确认

已核实：仓库有多种naive/pure/rflux实现；naive4对分段分数归一化并加序列beta，再直接赋给token advantages。

限制：根README缺失；一些基线分支使用±1及长度惩罚，不能把原仓库结果当作与我们的0/1协议同条件。
